## Context

См. [proposal.md](proposal.md), [explore.md](explore.md). В заказе уже есть типовые суммы со скидками, упаковки и режим НДС. Требуется исторический снимок, а не динамический вывод актуального прайса при открытии.

## Goals / Non-Goals

**Goals:** заполнение порога всеми маршрутами, сопоставимый расчёт, сохранение истории, серверные полномочия и причина исключения.

**Non-Goals:** изменение самой цены продажи, формула рентабельности, обновление всех исторических заказов при смене прайса, право обходить отсутствие закупочной цены.

## Decisions

### 1. Расширение и хранение

CFE в предлагаемом `extensions/OrderControlPrice/`, отдельный source set Юники.
ТЧ Товары: КонтрольнаяЦена в типовой точности цены и служебные данные происхождения снимка (дата получения, ключ параметров, исходная единица/валюта/НДС и вид цены). Пользовательская колонка только для чтения.
Шапка: ПричинаПродажиНижеКонтрольнойЦены. Отдельная роль «Разрешено продавать ниже контрольной цены» проверяется сервером под текущим пользователем.
Снимок, доступный для программной записи вместе с объектом, не считается доверенным: сервер сравнивает его с сохранённой версией и сам создаёт новые/изменённые снимки.

### 2. Источник цены

Администратор связывает настройку с конкретным видом «Контрольная цена» и базовым видом «Закупочная». Настроить штатную формулу коэффициента 1,09; перед использованием проверить её соответствие ТЗ. Поиск по имени допустим только как помощь первоначальной настройке с проверкой уникальности.
Сервер получает расчётный вид цены на дату ценообразования заказа через подтверждённый API УТ, проверяет наличие закупочной базы и приводит к валюте, упаковке и режиму НДС заказа.
Альтернатива ЦенаЗакупки/0,91 неверна математически; произвольная последняя закупка обходит заданный вид цены.

### 3. Жизненный цикл снимка

Единый сервис вызывается из ручного добавления, изменения номенклатуры/характеристики/упаковки, серверной обработки подбора, копирования и программного заполнения. Для обычной формы и самообслуживания — общая серверная реализация.
Ключ снимка включает номенклатуру, характеристику, единицу, валюту, дату ценообразования, НДС и прочие реально используемые параметры выбранного вида цены. Изменение ключа инвалидирует только соответствующие строки; смена валюты/даты/НДС шапки затрагивает все зависимые строки.
При открытии не изменять снимки. При проведении неизменённой строки сравнивать с сохранённым историческим порогом, даже если прайс уже изменён. Новая/изменённая строка и старый заказ без снимка получают серверный расчёт.
Копия документа — новый заказ: получить новые снимки по его дате/параметрам, не наследовать разрешение или причину прошлого исключения.

### 4. Сравнение и разрешение

На сервере после завершения типового расчёта скидок получить итоговую сумму строки и количество в соответствующей единице. Не вычитать скидки повторно. Если итог уже включает ручные/автоматические скидки — использовать его как числитель.
Обе цены привести к одному режиму НДС; типовые налоговые ставки/округление не заменять константой. Контрольная цена отображается/сравнивается с типовой точностью цены; произвольное снижение порога дополнительным округлением не допускается.
Проведение блокируется при отсутствии источника/порога/курса/коэффициента и некорректном количестве действующей строки. Отменённые строки заказа не участвуют в продаже.
Ниже порога: без роли отказ; с ролью требуется непустая после обрезки пробелов причина. Равенство допускается без исключения.
Роль повторно проверяется при каждом проведении. Клиентский признак разрешения и ОбменДанными.Загрузка не освобождают от проверки.

## Risks / Trade-offs

- [История против актуальности источника] → неизменённый подтверждённый снимок сохраняется, смена ключа требует нового источника.
- [Тихая подмена порога программным кодом] → сравнение сохранённых снимков и серверный пересчёт новых.
- [Двойное применение скидки/коэффициента упаковки] → примеры в обеих единицах и с обеими скидками.
- [Разные формы обходят заполнение] → общий сервис и обязательный контроль проведения.
- [Типовой API цены пока не выбран] → техническая задача чтения контракта и проверки формульного вида до написания интеграции.

## Migration Plan

Развернуть CFE и настроить два вида цен/формулу, роль назначить ограниченной группе. Существующие заказы не изменять при обновлении/открытии.
Для старого заказа без снимка первое проведение получает снимок и сохраняет его атомарно; отсутствие цены даёт понятный отказ.
Откат требует сохранить исторические пороги и причины; перед отключением оценить потерю обязательного контроля.

## Open Questions

При реализации подтвердить фактический API формульных цен УТ11 и источник итоговой суммы после всех скидок. Проектное допущение: причина на весь заказ; отменённые строки не проверяются, копирование рассчитывает новые снимки.

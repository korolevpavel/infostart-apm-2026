## ADDED Requirements

### Requirement: Источник контрольного вида цены

Система SHALL получать контрольную цену из настроенного вида «Контрольная цена», рассчитываемого как «Закупочная цена / 0,91» (маржа 9% от выручки), с однозначными ссылками на виды цен.

#### Scenario: Маржа 9 процентов

- **WHEN** закупочная цена равна 91 рублю за штуку
- **THEN** контрольная цена 100; прежняя наценка ×1,09, дающая 99,19, не применяется

#### Scenario: Не настроен источник

- **WHEN** отсутствует закупочная база, контрольный вид, корректная формула или курс пересчёта
- **THEN** проведение блокируется с указанием товара и недостающего источника даже для уполномоченного пользователя

### Requirement: Заполнение всех маршрутов

Система SHALL сохранять контрольную цену в строке заказа при ручном добавлении и подборе; для новой программной строки сервер обязан получать её самостоятельно.

#### Scenario: Ручной ввод

- **WHEN** в новой строке выбраны товар, характеристика и единица
- **THEN** контрольная цена заполнена без повторного открытия

#### Scenario: Подбор

- **WHEN** из подбора в обычной форме или форме самообслуживания добавлены несколько товаров
- **THEN** каждая новая строка получила свой порог

#### Scenario: Программное заполнение

- **WHEN** новая строка записывается/проводится без формы
- **THEN** порог рассчитывается сервером, клиентское значение не считается доверенным

### Requirement: Адресный пересчёт параметров

Система SHALL пересчитывать порог при смене номенклатуры, характеристики, единицы и других параметров источника; при редактировании формы изменять только зависимые строки, но при проведении заново рассчитывать все проверяемые строки.

#### Scenario: Изменение одной строки

- **WHEN** в заказе меняют характеристику одной позиции
- **THEN** пересчитан её порог, неизменённые строки сохраняют снимки

#### Scenario: Смена валюты шапки

- **WHEN** валюта заказа изменена
- **THEN** все зависимые пороги приведены к новой валюте; коэффициент упаковки применён однократно

#### Scenario: Смена даты источника

- **WHEN** изменена дата, используемая для выбора цены
- **THEN** затронутые снимки пересчитаны по новой дате

### Requirement: Исторический снимок

Система SHALL сохранять подтверждённый порог и параметры его происхождения, не обновлять их при простом открытии и при каждом проведении/перепроведении рассчитывать все проверяемые строки по ценам на дату проведения; исторический снимок использовать только для аудита, не для разрешения продажи. Точный смысл даты проведения и устройство истории остаются открытыми.

#### Scenario: Новый прайс после согласования

- **WHEN** заказ с сохранённым порогом 100 открывают после изменения закупочной цены
- **THEN** при открытии остаётся 100; при следующем проведении все проверяемые строки получают актуальный порог

#### Scenario: Подмена снимка

- **WHEN** программная запись пытается снизить порог неизменённой строки
- **THEN** для решения сервер заново получает актуальный порог; подменённый снимок не разрешает продажу, сохранённая история защищена

#### Scenario: Старый заказ

- **WHEN** заказ без снимков впервые проводят после установки расширения
- **THEN** сервер получает и сохраняет пороги атомарно; само открытие не меняло документ

#### Scenario: Копирование

- **WHEN** создан новый заказ копированием старого
- **THEN** пороги рассчитаны по параметрам нового заказа, причины исключения во всех строках очищены

### Requirement: Фактическая цена после скидок

Система SHALL сравнивать итоговую цену продажи за единицу после ручных/автоматических скидок с порогом в одинаковых валюте, единице и режиме НДС, не вычитать скидки повторно.

#### Scenario: Скидка ниже порога

- **WHEN** контрольная цена 100, итоговая цена после скидки 99
- **THEN** обнаружено отклонение 1 рубль

#### Scenario: Равенство

- **WHEN** итоговая сопоставимая цена равна контрольной
- **THEN** продажа допускается без полномочия на отклонение

#### Scenario: Разные единицы и НДС

- **WHEN** порог получен за штуку без НДС, заказ содержит упаковку с НДС
- **THEN** сначала выполняется сопоставимый пересчёт, затем сравнение; ложного отклонения нет

#### Scenario: Отменённая строка

- **WHEN** товарная строка заказа отменена
- **THEN** она не участвует в проверке действующей продажи

### Requirement: Полномочие и сохранённая причина

Система SHALL запрещать проведение ниже порога пользователю без отдельного полномочия; при наличии полномочия требовать непустую причину в каждой строке ниже порога и сохранять её в этой строке; для остальных строк причина не требуется. Конкретная роль/формат причины и реакция без них требуют подтверждения; отказ — прежняя проектная политика.

#### Scenario: Обычный менеджер

- **WHEN** менеджер без полномочия проводит строку по 99 при пороге 100
- **THEN** отказ содержит товар, фактическую и контрольную цены

#### Scenario: Право без причины

- **WHEN** уполномоченный сотрудник оставил причину одной из строк ниже порога пустой или из пробелов, даже если заполнена общая причина заказа
- **THEN** проведение запрещено

#### Scenario: Право и причина

- **WHEN** уполномоченный сотрудник указал содержательную причину в каждой строке ниже порога
- **THEN** проведение разрешено, причина каждой строки сохраняется и доступна при следующем открытии

### Requirement: Обязательность серверного проведения

Система SHALL повторять проверку полномочий, данных и отклонений при каждом проведении, независимо от интерфейса, клиентских флагов и режима загрузки.

#### Scenario: Прямое проведение

- **WHEN** обычный пользователь вызывает Записать с режимом проведения без формы
- **THEN** цена ниже порога блокируется тем же серверным правилом

#### Scenario: Полномочие отозвано

- **WHEN** ранее разрешённый заказ ниже порога перепроводит пользователь без текущего полномочия
- **THEN** новое проведение отклоняется; историческая причина не заменяет право

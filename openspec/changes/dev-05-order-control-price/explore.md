## Выбор подхода

Один серверный сервис рассчитывает порог через типовое ценообразование и выдаёт сохранённый снимок: цена, валюта/единица/НДС, дата получения, ключ параметров источника.
Нельзя подменять источник умножением любой последней закупки на 1,09: требование задаёт именно вид цены. Настройка должна ссылаться на виды цен устойчивыми ссылками, не искать их по наименованию при каждом проведении.
Процент — наценка, поэтому деление на 0,91 неверно.

```text
Ручной ввод / подбор / изменение параметров → серверный вид цены → снимок строки
Проведение → итог после скидок ↔ сохранённый порог → право + причина → разрешить/отказать
```

## Риски и допущения

- При новом открытии неизменённый снимок не актуализируется; при смене валюты, даты ценообразования, единицы, номенклатуры, характеристики и иных параметров затронутые снимки обновляются.
- Обычная программная запись не может передать произвольно заниженный порог: для новых/изменённых ключей сервер получает цену сам; для неизменённых ключей берётся защищённый ранее сохранённый снимок.
- Для старых заказов без снимка он рассчитывается при первом проведении/явном заполнении, но не при открытии.
- Причина сохраняется в шапке и покрывает все отклонения данного заказа; строковые причины не требуются ТЗ.
- Отсутствие закупочной базы/контрольного вида цены блокирует проведение даже уполномоченному сотруднику. Нулевую закупочную базу считаем некорректной настройкой.
- Суммы скидок нельзя вычитать второй раз из уже итоговой суммы. Нужен эксперимент типовой строки с ручной и автоматической скидкой.
Эталон: 2 400 × 1,09 = 2 616; итог 2 590 < 2 616 — отказ без права, с правом требуется причина.

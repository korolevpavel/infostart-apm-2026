## Context

См. [proposal.md](proposal.md), [explore.md](explore.md). В типовом ПередЗаписью плана продаж уже есть даты запрета и Планирование.ПроверитьСтатусУтвержден, затем пересчёты строк. Простого UI-снятия блокировки недостаточно.

## Goals / Non-Goals

**Goals:** безопасно менять выбранные поля утверждённого плана, защищать от прямой записи и гонки зависимостей, регистрировать каждую попытку.

**Non-Goals:** изменение сумм/товаров/статуса/организации/периода, снятие утверждения, обход дат запрета, изменение документа месячных лимитов из DEV-1C-04.

## Decisions

### 1. Расширение и полный серверный запрет

CFE в предлагаемом `extensions/ApprovedPlanEdit/`. Заимствовать три типа планов и формы, добавить роль, диалог, серверный сервис разрешений.
Начальный белый список — Ответственный и Комментарий. При сохранении читать сохранённый утверждённый объект и сравнивать все реквизиты/табличные части, а не только UI-поля.
Проверка выполняется независимо от ОбменДанными.Загрузка и дополнительных свойств. Смена статуса с Утвержден не должна делать объект свободным: решение опирается на сохранённое состояние.
Типовые права/запреты дат продолжают действовать. Для типовой проверки статуса нужен узкий перехват только целевого плана с валидным разрешением, без глобального отключения Планирование.ПроверитьСтатусУтвержден.
После типовых ПередЗаписью/ПриЗаписи повторно подтвердить неизменность защищённых данных, чтобы автоматические пересчёты не исказили утверждённые суммы. Сохранение без бизнес-изменений допускается лишь без побочных изменений.

### 2. Организация плана сборки

У плана сборки/разборки в исходниках отсутствует Организация. Добавить префиксованный реквизит-ссылку на Catalog.Организации в расширении и поле формы; требовать перед утверждением.
Для прежних утверждённых планов подготовить заполнение организации по подтверждённым данным, без вывода из одного склада. До завершения подготовки утверждённый план сборки без организации с тем же сценарием/пересечением считается неопределённой потенциальной зависимостью: разрешение не выдаётся, показывается причина.
Альтернатива считать любой план сборки всей базы зависимым нарушает требование организации; исключить все такие планы тоже нельзя.

### 3. Разрешение формы

Сервер выдаёт криптографически непредсказуемый идентификатор и хранит запись: пользователь, сеанс, экземпляр формы, ссылка плана, версия/снимок, выбранные поля, время, состояние. Клиент не выбирает состав серверной записи.
Разрешение живёт в серверном хранилище, привязанном к форме; закрытие отзывает его, завершение сеанса также делает его недействительным. Повторное открытие и другая форма документа не наследуют доступ.
После успешного сохранения обновлять версию разрешения и продолжать только в этой форме с тем же списком; при конфликте версий отозвать и потребовать новый запрос.
Прямая запись проходит тот же сервис и требует действительного разрешения текущего контекста; произвольное ДополнительныеСвойства.Разрешено не принимается. Доверенный программный маршрут может получить краткоживущее разрешение для одной серверной операции с теми же проверками/аудитом.

### 4. Проверка зависимостей и конкурентность

Кандидаты: утверждённые ПланЗакупок и ПланСборкиРазборки той же организации/сценария, интервалы включительно пересекаются. Возвращать пользователю тип, ссылку, номер, дату, начало/конец периода; пустые организация/сценарий текущего плана — отказ с пояснением.
Повторить проверку при сохранении в той же транзакции, что изменение плана. Общий регистр-координатор с ключом организация/сценарий служит объектом управляемой блокировки.
Утверждение/перенос периода/смена организации или сценария зависимых планов должны брать тот же ключ; блокировка только на стороне плана продаж не закрывает гонку. При изменении ключа зависимого плана блокировать старый и новый в стабильном порядке.
Альтернатива «дважды SELECT без общего протокола» оставляет окно между проверкой и записью.

### 5. Устойчивый аудит

Отдельные события запроса, отказа, разрешения, сохранения и отзыва; итог разрешено/отказано, причина, пользователь, дата/время сервера, компьютер, ссылка, поля, идентификатор попытки.
Имя компьютера получать из доступного контекста сеанса/соединения, не из произвольного текстового поля диалога. Для веб-клиента подтвердить доступность значения; если имя нельзя получить достоверно, показать это ограничение до ввода механизма, не записывать имя сервера как компьютер пользователя.
Отказы писать через журнал регистрации/другой подтверждённый независимый канал с нетранзакционным режимом. Обычный регистр в откатываемой транзакции документа не выполняет требование. Успешный результат фиксировать после подтверждённой записи; включить корреляцию с попыткой, чтобы не заявлять успешное сохранение при откате.
Пользователь роли корректировки не получает права редактировать/удалять аудит.

## Risks / Trade-offs

- [Гонка утверждения зависимости] → общий ключ блокировок на обоих маршрутах.
- [Потеря аудита отказов] → независимый канал, эксперимент отката обязателен.
- [Типовой пересчёт меняет защищённые поля] → сравнение до и после; отсутствие изменений строк — условие успеха.
- [Старые сборочные планы без организации] → подготовка данных и безопасный отказ при неопределённости.
- [Перенос разрешения между формами] → привязка к форме/версии, серверный отзыв.
- [Смена релиза типовой проверки статуса] → узкий перехват и регрессионная проверка после обновлений.

## Migration Plan

Добавить организацию плану сборки, подготовить исторические данные, проверить оба типа зависимостей. Создать роль без назначения обычным пользователям; проверить аудит в целевых типах клиентов.
После сценариев параллельной записи назначить роль уполномоченным сотрудникам. При откате отозвать все разрешения, сохранить аудит и соответствия организаций; отключение механизма не должно снимать типовую защиту.

## Open Questions

Технически подтвердить доступное имя компьютера в целевом клиенте, устойчивый канал аудита и безопасный узкий перехват типовой проверки статуса. Начальный набор полей ограничен Ответственным и Комментарием; иные поля требуют расширения бизнес-контракта.

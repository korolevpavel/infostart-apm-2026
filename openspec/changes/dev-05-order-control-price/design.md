## Context

См. [proposal.md](proposal.md), [explore.md](explore.md). В заказе уже есть типовые суммы со скидками, упаковки и режим НДС. При открытии снимок сохраняется; при каждом проведении все строки пересчитываются по актуальному порогу, а исторический снимок служит только аудиту.

## Goals / Non-Goals

**Goals:** заполнение порога всеми маршрутами, сопоставимый расчёт, актуальный контроль при проведении и сохранение истории для аудита, серверные полномочия и причина исключения.

**Non-Goals:** изменение самой цены продажи, обновление всех исторических заказов при смене прайса, право обходить отсутствие закупочной цены.

## Decisions

### 1. Расширение и хранение

CFE в предлагаемом `extensions/OrderControlPrice/`, отдельный source set Юники.
ТЧ Товары: КонтрольнаяЦена в типовой точности цены и служебные данные происхождения снимка (дата получения, ключ параметров, исходная единица/валюта/НДС и вид цены). Пользовательская колонка только для чтения.
ТЧ Товары: ПричинаПродажиНижеКонтрольнойЦены в каждой строке ниже порога; общей причины шапки недостаточно. Отдельная роль «Разрешено продавать ниже контрольной цены» проверяется сервером под текущим пользователем.
Снимок, доступный для программной записи вместе с объектом, не считается доверенным: сервер защищает историю и сам получает актуальный порог для проведения независимо от переданного снимка.

### 2. Источник цены

Администратор связывает настройку с конкретным видом «Контрольная цена» и базовым видом «Закупочная». Настроить формулу ЗакупочнаяЦена / 0,91 для маржи 9% от выручки; перед использованием проверить её соответствие ТЗ. Поиск по имени допустим только как помощь первоначальной настройке с проверкой уникальности.
Сервер получает расчётный вид цены на дату проведения (точный смысл даты ещё не определён) через подтверждённый API УТ, проверяет наличие закупочной базы и приводит к валюте, упаковке и режиму НДС заказа.
При закупочной 91 порог равен 100; прежняя наценка ×1,09 отменена. Конкретный источник закупочной цены и API формульного вида ещё требуется подтвердить; произвольную последнюю закупку не считать подтверждённым ответом.

### 3. Жизненный цикл снимка

Единый сервис вызывается из ручного добавления, изменения номенклатуры/характеристики/упаковки, серверной обработки подбора, копирования и программного заполнения. Для обычной формы и самообслуживания — общая серверная реализация.
Ключ снимка включает номенклатуру, характеристику, единицу, валюту, дату ценообразования, НДС и прочие реально используемые параметры выбранного вида цены. Изменение ключа инвалидирует только соответствующие строки; смена валюты/даты/НДС шапки затрагивает все зависимые строки.
При открытии не изменять снимки. При каждом проведении/перепроведении пересчитывать все проверяемые строки по ценам на дату проведения, включая неизменённые строки и старые заказы. Исторический снимок сохраняется для аудита и не даёт разрешения на продажу. Состав, момент формирования и место хранения истории требуют уточнения; ключ параметров/происхождение — проектное предложение.
Копия документа — новый заказ: получить новые снимки по его дате/параметрам, не наследовать разрешение, очищать причины во всех строках; менеджер заново обосновывает каждую строку ниже актуального порога.

### 4. Сравнение и разрешение

На сервере после завершения типового расчёта скидок получить итоговую сумму строки и количество в соответствующей единице. Не вычитать скидки повторно. Если итог уже включает ручные/автоматические скидки — использовать его как числитель.
Обе цены привести к одному режиму НДС; типовые налоговые ставки/округление не заменять константой. Контрольная цена отображается/сравнивается с типовой точностью цены; произвольное снижение порога дополнительным округлением не допускается.
Проведение блокируется при отсутствии источника/порога/курса/коэффициента и некорректном количестве действующей строки. Отменённые строки заказа не участвуют в продаже.
Ниже порога: без роли отказ; с ролью требуется непустая после обрезки пробелов причина в каждой строке ниже порога. Для остальных строк причина не требуется. Серверный отказ без роли/причины и формат непустого текста — прежнее проектное решение; точное имя роли и формат нужно подтвердить. Равенство допускается без исключения.
Роль повторно проверяется при каждом проведении. Клиентский признак разрешения и ОбменДанными.Загрузка не освобождают от проверки.

## Risks / Trade-offs

- [История вместо актуального контроля] → каждый раз пересчитывать все строки, снимок использовать только для аудита.
- [Тихая подмена порога программным кодом] → актуальный серверный пересчёт при каждом проведении и защита истории.
- [Двойное применение скидки/коэффициента упаковки] → примеры в обеих единицах и с обеими скидками.
- [Разные формы обходят заполнение] → общий сервис и обязательный контроль проведения.
- [Типовой API цены пока не выбран] → техническая задача чтения контракта и проверки формульного вида до написания интеграции.

## Migration Plan

Развернуть CFE и настроить два вида цен/формулу, роль назначить ограниченной группе. Существующие заказы не изменять при обновлении/открытии.
При каждом проведении старого заказа получать актуальный порог, история не освобождает от контроля. Прежняя политика отказа при отсутствии цены сохраняется как допущение до уточнения источника/обработки отсутствующей цены.
Откат требует сохранить исторические пороги и причины; перед отключением оценить потерю обязательного контроля.

## Open Questions

- Что означает «дата проведения»: текущий момент операции, дата документа или иной момент?
- Каков конкретный источник закупочной цены, API формульного вида/итоговой суммы после скидок, курс, округление и обработка отсутствующей цены? Прежний серверный отказ при отсутствии данных — допущение.
- Каковы состав, момент формирования и место хранения аудиторского снимка?
- Подтвердить точное имя роли, формат построчной причины и реакцию при её отсутствии/отсутствии роли. Отмена строки и адресное обновление в форме остаются проектными правилами; проведение в любом случае пересчитывает все проверяемые строки.

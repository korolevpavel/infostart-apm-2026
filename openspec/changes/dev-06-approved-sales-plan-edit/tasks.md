## 1. Контракты и подготовка данных

- [ ] 1.1 Через Юнику прочитать Планирование.ПроверитьСтатусУтвержден и цепочку записи плана; выбрать узкую точку разрешения без отключения типовых дат запрета.
- [ ] 1.2 Технически подтвердить хранение разрешения с привязкой к форме/сеансу, контекст пользователя/сеанса/типа клиента, имя компьютера либо «недоступно» в веб-клиенте, доверенный источник IP и независимый аудит отказа после отката.
- [ ] 1.3 Создать CFE/source set extensions/ApprovedPlanEdit с заимствованием трёх типов планов; добавить роль, диалог, серверные сервисы и регистр-координатор.
- [ ] 1.4 Уточнить охват объектов/статусов, уровни полей и границы периодов; проверить наличие менеджера товарной строки и при отсутствии добавить его расширением; организацию сборки не добавлять.

## 2. Разрешение и интерфейс

- [ ] 2.1 Защитить утверждённый план в обычной форме и самообслуживании, добавить команду только для роли корректировки.
- [ ] 2.2 Реализовать белый список Ответственный/Комментарий/МенеджерСтроки, выбор подмножества и серверную проверку непустого допустимого набора.
- [ ] 2.3 Реализовать поиск двух типов зависимостей по сценарию/пересечению (границы уточнить); организацию учитывать только у закупок, сборка общая для группы, возврат ссылок/номеров/дат/периодов.
- [ ] 2.4 Реализовать серверную выдачу разрешения с пользователем, сеансом, формой, ссылкой, версией и полями; отозвать при закрытии/конфликте, запретить перенос.
- [ ] 2.5 Реализовать независимый аудит запроса и результата выдачи/отказа с пользователем/сеансом/типом клиента, проверенным именем компьютера либо «недоступно» в браузере, IP только из доверенного контекста и идентификатором попытки.

## 3. Запись и конкурентность

- [ ] 3.1 Реализовать сравнение всех данных с сохранённой утверждённой версией до записи, запрет изменения невыбранных полей и смены статуса для обхода.
- [ ] 3.2 Подключить обязательный контроль прямой записи/загрузки, проверить роль и токен текущего контекста, не доверять дополнительным свойствам объекта.
- [ ] 3.3 Ввести общий протокол блокировки по сценарию для всех организаций при сохранении плана продаж и утверждении/смене ключей планов закупок и сборки.
- [ ] 3.4 Повторять поиск зависимостей под блокировкой в транзакции сохранения; блокировать старые/новые ключи в стабильном порядке.
- [ ] 3.5 После типового пересчёта повторно проверить защищённые данные; при успехе обновить версию разрешения формы, при конфликте отозвать.
- [ ] 3.6 Реализовать устойчивый аудит сохранения/отказа, корреляцию с результатом транзакции и запрет изменения аудита пользователем корректировки.

## 4. Валидация и приёмка

- [ ] 4.1 Выполнить unica.check всех изменённых объектов/BSL и git diff --check; получить контракт unica.run {} и собрать CFE.
- [ ] 4.2 Проверить роль/отсутствие роли, только Ответственный, только Комментарий, МенеджерСтроки и комбинации трёх полей, запрет добавления/удаления строк и попытку изменения сумм/товаров/статуса и программный обход.
- [ ] 4.3 Проверить оба типа зависимостей: организация только у закупок, общая сборка с тем же сценарием, частичное пересечение, общая граница, отсутствие пересечения и неутверждённые планы.
- [ ] 4.4 Проверить закрытие/повторное открытие, вторую форму, чужой токен/версию и типовую дату запрета; права не должны расширяться.
- [ ] 4.5 Двумя сеансами проверить появление зависимости после разрешения и гонку утверждения с сохранением; зафиксировать порядок и результат.
- [ ] 4.6 Искусственно откатить отказную запись и подтвердить сохранность аудита пользователя/сеанса/типа клиента/компьютера либо «недоступно» в веб-клиенте/полей/итога; проверить успешный аудит без ложного успеха при откате.
- [ ] 4.7 Сохранить журнал runtime-сценариев и скриншоты диалога/отказов; подготовить назначение роли, добавление менеджера строки при необходимости, отзыв разрешений и откат.

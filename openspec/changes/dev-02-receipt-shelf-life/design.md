## Context

См. [proposal.md](proposal.md) и [explore.md](explore.md). Серия УТ уже хранит ДатаПроизводства и ГоденДо. Остаток зависит от документа, поэтому хранение одного «актуального процента» в серии непригодно.

## Goals / Non-Goals

**Goals:** проверять все поступающие серии до движений, однозначно рассчитывать календарные дни, сохранять поддержку типовой базы.

**Non-Goals:** автоматическое исправление исторических серий, перепроведение всех поступлений при правке серии, контроль отгрузки покупателю, изменение складской политики серий.

## Decisions

### 1. Расширение и модель данных

Отдельное расширение, предлагаемые исходники `extensions/ReceiptShelfLife/`, отдельный source set Юники при реализации. Заимствовать серии, соглашения, приобретение, приходный ордер и формы; добавить префиксованные объекты.
Серия: повторно использовать ДатаПроизводства; добавить ПолныйСрокХраненияДней (целое положительное). Дата окончания — вычисление начала дня производства + N календарных дней; при сохранении синхронизировать ГоденДо и не разрешать расходящиеся ручные значения.
Соглашение: МинимальныйОстатокПроцент (0..100) и признак ПорогНастроен, различающий отсутствие настройки и явный ноль.
Альтернатива дублирования даты изготовления создаёт два источника истины и отклоняется.

### 2. Единый расчёт на сервере

Общий серверный модуль принимает дату документа, соглашение и таблицу фактических серий. Дни считаются между началами дней; остаток R = N − прошедшие дни; процент 100*R/N. Отказ при R<0 независимо от порога. Пустой порог даёт предупреждение и список товаров ответственному за качество, не отменяя запрета просрочки. Явно настроенные 0% означают эффективный минимум 30%: 29% запрещены, 30% допустимы. Для положительного порога действует его значение. Формула дней, округление и трактовка дня истечения — прежние проектные решения, требующие подтверждения.
Для решения сравнивать 100*R с ЭффективныйПорог*N для настроенного порога; округлять до одного знака лишь представление. Сообщение содержит товар, серию, фактический процент, минимум и причину. Если округлённые проценты скрывают различие, дополнительно показать дни/повышенную точность в пояснении.

### 3. Сбор серий и момент проверки

Нормализовать Товары.Серия и отдельную ТЧ Серии по стандартной политике учёта; не складывать дубли одной поставки повторно. Набор проверяемых серий должен покрывать всё поступающее серийное количество.
Подключить контроль до типовых движений ОбработкаПроведения, сохранять уже установленный Отказ. Серверный вызов/обмен не пропускает проверку. Формы показывают расчёт для удобства, но не дают разрешение на проведение.
При ордерной схеме блокирующая проверка срока выполняется только при проведении приходного ордера по его фактическим сериям и дате; приобретение без серий пропускается этим контролем. При неордерной схеме проверять приобретение по его дате. Уточнить точные точки подключения и поведение отсутствующих обязательных серий в самом ордере. С DEV-1C-03 согласовать оба маршрута, не возвращая проверку срока в ордерное приобретение.

### 4. Интерфейс

На форме серии показывать дату изготовления, срок в днях, дату окончания и вычисленный процент для явно показанной даты расчёта. При переходе из документа дата передаётся; без документа начальное значение — текущая дата сеанса с возможностью выбора.
На форме поступления обеспечить просмотр результата каждой серии и обновление при смене даты. Сохранять процент как независимый бизнес-реквизит не требуется.

## Risks / Trade-offs

- [Нет серий в приобретении при ордерной политике] → контроль срока перенесён в приходный ордер; проверить его серии и дату.
- [Изменение серии во время проведения] → читать согласованные реквизиты/порог в одной транзакции с нужными блокировками.
- [Старые серии без срока] → отчёт подготовки и ручное подтверждение; не вычислять недостоверные даты.
- [Порог не настроен] → предупреждение и список качества; канал доставки списка и миграция старых нулей остаются открытыми.
- [Общие обработчики с DEV-1C-03] → проверка совместного подключения расширений без замещения всей типовой процедуры.

## Migration Plan

Создать CFE, настроить пороги соглашений и заполнить обязательные данные существующих серий. На копии базы проверить обычную и ордерную схемы, пакетное проведение и перепроведение.
Откат — отключить расширение после оценки необходимости контроля; сохранить резервную копию дополнительных данных. Типовое ГоденДо остаётся корректной датой окончания, массовые исторические правки не выполняются автоматически.

## Open Questions

- Уточнить точные объекты/обработчики ордерного маршрута и поведение при отсутствии серии в приходном ордере.
- Подтвердить формулу остатка, округление и день истечения срока; wiki этих деталей не задаёт.
- Подтвердить хранение пустого порога отдельно от нуля (предложен ПорогНастроен), миграцию старых нулей и канал списка товаров для ответственного за качество.
